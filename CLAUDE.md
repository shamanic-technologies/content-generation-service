# Project: content-generation-service

Microservice that generates personalized content (emails, calendar events, etc.) via chat-service (which handles LLM calls, key resolution, billing, and cost tracking), with PostgreSQL storage and run tracking via runs-service.

## Commands

- `pnpm test` — run all tests (Vitest)
- `pnpm test:unit` — run unit tests only
- `pnpm test:integration` — run integration tests only
- `pnpm run build` — compile TypeScript + generate OpenAPI spec
- `pnpm run dev` — local dev server (tsx watch)
- `pnpm run generate:openapi` — regenerate `openapi.json` from Zod schemas
- `pnpm db:generate` — generate Drizzle migrations
- `pnpm db:migrate` — run database migrations
- `pnpm db:push` — push schema to database
- `pnpm db:studio` — open Drizzle Studio

## Platform-owned prompt templates

The `prompts` table stores prompt templates keyed by `type` (unique). Two ownership tiers:

1. **Platform-owned** (`org_id IS NULL`) — source of truth lives in code under `src/lib/*-template.ts`. Reconciled on every boot by `registerPlatformTemplates()` via `INSERT ... ON CONFLICT (type) DO UPDATE` — body, variables metadata, and `updated_at` always match the source. Skip-if-exists is forbidden here because changes to the source must propagate without manual reseed.
2. **Org-tuned versions** — created via `PUT /prompts` under a versioned slug (`<type>-v2`, `<type>-v3`, …). Different `type` value → never touched by the platform reconcile loop.

To add a new platform template: create `src/lib/<name>-template.ts` exporting `TYPE`, `TEMPLATE`, and `VARIABLES: Array<{ name, description }>`, then append the entry to `PLATFORM_TEMPLATES` in `src/lib/register-platform-templates.ts`.

The `variables` array is the self-describing contract callers use to construct the request body for `POST /generate` and `POST /generate-expert-quote-pitch`. Keep descriptions precise — external callers discover input shape via `GET /platform-prompts?type=<type>`.

### `expert-quote-pitch` input contract (three generic-JSON blobs)

The request type stays `variables: Record<string, unknown>` (DIS-52 — no per-field Zod schema; callers keep JSON flexibility). Required-ness is enforced at **runtime** by `assertExpertQuotePitchVariables(variables, declaredVariables)`, called in the route before any LLM spend → **400 fail-loud** if anything is missing/empty. The platform template declares **three generic-JSON variables**, each just checked for **presence + non-empty** — NO per-field structural validation:
1. **`expert`** — freeform JSON for the person whose quote gets published (name/title/bio/photo/linkedin/answer angle+context). The old granular `expertName`/`expertTitle`/`expertBio`/`expertPhotoUrl`/`expertLinkedIn`/`expertAnswerContext` are folded into this one blob.
2. **`brands`** — freeform JSON for the brand(s) the expert represents. Multibrand default (usually an array), but ANY non-empty shape passes. The old required brand sub-fields (`brandName`/`brandUrl`/…) are gone — a bare `{ name }` is accepted.
3. **`journalistRequest`** — freeform JSON describing the journalist's request.

The guard is intentionally NOT severe on the inner shape — the blobs are markdown-coerced straight into the prompt, so the model reads whatever the caller sends. (This deliberately reversed the old all-required-per-sub-field guard, which 400'd pitches on missing attribution-only fields like `brandLogoUrl`.)

**Changing the variable set is a hard break** for callers (journalists-quotes-service / windmill DAG + dashboard `/draft` via api-service proxy) AND invalidates every existing org fork (`expert-quote-pitch-v*`, old token set). When the contract changes, ship a data migration that `DELETE`s the stale `feature_prompt_assignment` rows (`prompt_type LIKE 'expert-quote-pitch-v%'`) + the stale fork rows (`prompts.type LIKE 'expert-quote-pitch-v%'`) so the feature falls back to the rebuilt platform default. See `drizzle/0027_reset_expert_quote_pitch_forks_generic_json.sql` (latest; `0024` was the prior reset). The api-service proxy is pass-through (body owned by this service) — no gateway change.

**BACK UP THE FORKS BEFORE THE RESET DELETE — org forks are hand-tuned prompt copy, not disposable.** A reset migration's `DELETE FROM prompts WHERE type LIKE 'expert-quote-pitch-v%'` destroys real org customization (e.g. org `f0420eb5` had `v2…v5`, ~a month of tuning, `v5` actively assigned to feature `pr-expert-quote-opportunities`). Recovery now depends entirely on whatever backup the self-hosted Postgres box holds — there is no Neon PITR window any more, so treat the DELETE as unrecoverable. Before shipping any `expert-quote-pitch-v%` reset: (1) dump the fork rows + their `feature_prompt_assignment` rows to a file (`SELECT json_agg(...) FROM prompts WHERE type LIKE 'expert-quote-pitch-v%'`), commit it under `drizzle/` or `.context/`; (2) after the contract change, re-port each active fork's BODY onto the new token set (the fork's `{{tokens}}` only live in its Inputs block — the rest of the tuned body is reusable verbatim) and re-INSERT under a fresh `-vN` + re-assign. Incident 2026-07-03: `0027` wiped `f0420eb5`'s `v5`; restored via a PITR branch (`neonctl branches create --parent <ts-before-delete>`) → the `v5` body ported to the 3-blob contract as `expert-quote-pitch-v6`, feature reassigned. The DELETE-without-backup should never have shipped in `0027`.

## Shared templates are brand/offer neutral (`src/lib/template-neutrality*.ts`)

Every `prompts` row is global by `type`, and the dashboard Copilot creates and forks templates live from one client's conversation. A template whose FIXED text names that client (brand, offer, price, result figure, person) would write a stranger's facts into every other brand's emails. So every route that STORES a template judges it first: `POST /prompts`, `POST /platform-prompts`, `PUT /prompts`, `PUT /prompt-assignments`.

- **Classification is chat-service Jev, never a regex or `/complete`.** The template is the judgment `state`; each passage (line → sentence, plus each variable description) is one `noul` question. Yes-probability ≥ 0.5 → refused. The channel the content is written for (LinkedIn, Featured.com) is exempt in the wording: v1 refused the platform `expert-quote-pitch` at p=0.6 for naming Featured.com. Before changing the wording, run it against real templates (`cold-email-v49`, `expert-quote-pitch`, `expert-quote-pitch-v6`) AND a specific probe in prod: v2 measured 0.97 on the probe and ≤0.26 on those three. Org routes call `POST /orgs/judgments` under the inbound identity (org-billed); `PUT /prompt-assignments` without `x-run-id` opens a root run for it; `POST /platform-prompts` and the template-dynasty writes call `/internal/platform-judgments` with body `support: { kind: "platform_llm", reason }` (PLATFORM-CALLER-RUN-1024: no run of ours stands behind a template write, a template is no outcome; never an inbound `x-run-id` on that tier; reasons in `src/lib/platform-judgment-support.ts`, pinned by `tests/unit/judgments-client.test.ts`). chat-service declares the input-token cost itself; this service declares nothing.
- **Judged once, persisted**: `template_neutrality_judgments`, keyed on sha256(rule version + body + variables). A resubmission reads the stored verdict, no spend. Changing the wording, splitting or threshold → bump `TEMPLATE_NEUTRALITY_VERSION`.
- **Refusal = 422** `{ error, code: "TEMPLATE_NOT_NEUTRAL", passages: [{ passage, location, probability }] }`; the fix is to turn the specific part into a declared `{{variable}}`. A Jev failure keeps 402/429, else 502, `code: "TEMPLATE_NEUTRALITY_CHECK_FAILED"`. Nothing is stored unjudged.
- **A derived version is judged on what it ADDS** (`PUT /prompts`, `PUT /prompt-assignments`, i.e. every dynasty upgrade): passages present unchanged in the source type (same text, same location) are not questions; the full template stays the judgment `state`. A reworded sentence is new text. Templates stored before the check (`cold-email-v12`, `blind-discovery-email-v9`) carry passages the check would cite, and refusing an edit for them made every upgrade impossible (PARA-UPGRADE-1016). The source's passages are part of the verdict key, so a derived verdict is never served to a non-derived write; without a source the key is unchanged.
- **Only NEW rows are judged.** Existing templates are untouched; an idempotent create of an existing type and a byte-identical `PUT /prompts` store nothing and are not judged. The boot reconcile of code-owned platform templates (`registerPlatformTemplates`) is not judged.

## Blind templates keep the client anonymous (`src/lib/blind-template-rule.ts`, BLIND-WRITER-1017, run-time part withdrawn BLIND-WRITER-REVERT-1017)

A template type starting `blind-discovery-email` or `feedback-request-blind-email` (`isBlindTemplateType`) promises the prospect never learns who the client is from the email; features-service tags "Blind angle" on the TYPE alone. **The template text is the guarantee, nothing checks the email** (owner 2026-10-17: « We dont want to spend extra money!!! The template instructions should be enough, we are ok with some NOISE »; supersedes the 2026-10-17 run-time guard of v0.36.1). A blind `/generate` or `/preview-email` is one completion, exactly like a named one: no brand read for anonymity, no rule appended, no literal check, no rewrite, no `BLIND_CLIENT_NAMED`/`BLIND_BRAND_UNREADABLE`. Some emails naming the client are accepted. Do NOT re-add a per-email guard (pinned by `tests/unit/generate-blind.test.ts`).

- **At template save** (`blind-template-rule.ts` + `assertBlindTemplateKeepsClientAnonymous`, run from `assertTemplateNeutral` when `type` is blind): Jev `noul` per passage, "does it tell/allow the writer to put the client's name, website or a link in the email". EVERY passage is judged, inherited ones included (unlike neutrality): an upgrade of `blind-discovery-email-v34` passes only once its licensing passages are deleted. 422 `BLIND_TEMPLATE_REVEALS_CLIENT` with the passages. One judgment per new template, never per email; verdict persisted in `template_neutrality_judgments` (`rule_version = blind-1`). Measured 2026-10-17: v34/v36 refused at 0.82 to 0.94, v16 at 0.85 to 0.98, v26 at 0.75; v15 and `feedback-request-blind-email-v1` ≤ 0.12. Changing the wording → bump `BLIND_TEMPLATE_RULE_VERSION` and re-measure on those.

## Template dynasties (TPL-DYNASTY-1021-CG, owner 2026-10-21)

A dynasty is ONE email strategy on ONE pipe (`featureSlug` x `legKey`), cross-org; the same strategy on two pipes is two dynasties. Workflows name a dynasty and write with its HEAD (latest version), so a fix added as a version reaches every workflow of that kind of email, and stats pool across versions. `email_generations.prompt_type` keeps the exact version used. Rules: `src/lib/template-dynasties.ts` (leaf), I/O: `template-dynasty-query.ts`.

- **Storage**: `template_dynasties` (slug PK, name unique per pipe, description unique globally and shown to clients, signature unique per pipe and internal, identity `blind|named`, feature_slug, leg_key) + `template_dynasty_versions` (dynasty_slug, prompt_type FK `prompts.type`, position; head = max position). **A template belongs to ONE dynasty** (owner 2026-10-21: « complètement interdit, et doit être interdit en dur »): unique index `idx_template_dynasty_versions_type`, and every write refuses first with 409 `TEMPLATE_IN_OTHER_DYNASTY` (`createDynasty` over stored templates, `POST …/versions {type}`). `drizzle/0038` split the 21 texts that sat in a cold-reply AND a cold-click dynasty: the reply dynasty keeps the original, the click one holds a copy `<family>-website-visit-vN` at the same position, `prompts.copied_from` = the original (served as `versions[].copiedFrom`), because that pipe's past emails carry the original name. Templates in no dynasty stay unattached. Seeded by `drizzle/0036` from the 26 owner-validated dynasties (fixture `tests/fixtures/template-dynasties-2026-10-21.json`); the version seed joins `prompts`, so an empty CI database gets dynasties without versions.
- **Contract (API key only, no identity headers)**: `GET /internal/template-dynasties?featureSlug=&legKey=` → `{ dynasties }`; `GET /internal/template-dynasties/{slug}` → dynasty `{ slug, name, description, signature, identity, featureSlug, legKey, head, versions: [{ type, position, status, addedAt }] }` (404 `DYNASTY_NOT_FOUND`); `GET …/{slug}/head` → `{ dynasty, template }` (`template` = `PromptResponse`, send `template.type` as `/generate` `type`); `POST …/{slug}/versions` `{ prompt, variables }` (new text) or `{ type }` (an already-stored template; 409 `ALREADY_IN_DYNASTY`, 400 `UNKNOWN_TEMPLATE`) → 201 `{ dynasty, template }`, the new head; `POST /internal/template-dynasties` creates one over existing templates (`versions` oldest first) OR from a brand-new text (`template: { prompt, variables, type? }`, exactly one of the two; TPL-DYNASTY-FROM-TEXT-1021): stored as version 1 and head under `type` or `<slug>-v1`, refused before any write on `VARIABLES_MISMATCH` (400), `TEMPLATE_TYPE_TAKEN` / `TEMPLATE_TWIN` / `DYNASTY_CONFLICT` (409), neutrality judged in full + the blind rule when the dynasty is blind (422), Jev billed to the platform.
- **A new version**: stored as the next free `<head family>-vN` (type families and their prefix readers unchanged). Refused: text byte-identical to ANY other stored template → 409 `TEMPLATE_TWIN` + `twinType`; a `{{token}}` the head does not declare → 400 `VARIABLE_NOT_IN_HEAD` (every workflow on the dynasty sends the head's variables; dropping one is fine); `variables` not exactly the text's tokens → 400 `VARIABLES_MISMATCH`; neutrality (judged on what it adds to the head) and, when the DYNASTY is blind, the blind rule → 422; Jev billed to the platform. Identity is the dynasty's, never the type prefix: several historical types say otherwise (`blind-discovery-email-*` in named dynasties).
- **A dynasty's text keeps its identity (TPL-NAMED-HEAD-1023, owner 2026-10-23: identity is binary)**: every new version (`POST …/versions`, both shapes), every new-text dynasty AND the head of a dynasty created over stored templates is judged by `assertTemplateKeepsDynastyIdentity`: blind → the blind rule; named → `named-template-rule.ts` (Jev `noul` per passage, inherited included: "does it tell the writer to keep the client anonymous"), 422 `NAMED_TEMPLATE_HIDES_CLIENT`, verdict persisted (`rule_version = named-1`). ## Tracking / attribution headers

Identity + attribution headers (`x-run-id`, `x-campaign-id`, `x-brand-id`, `x-workflow-slug`, `x-feature-slug`, `x-audience-id`) flow through ONE allowlist in `src/lib/tracking.ts` — `TRACKING_HEADER_KEYS`. **Never cherry-pick header fields per client.** To add a new attribution dimension:
1. Add the field to the `Tracking` interface + a `[field, "x-header"]` entry to `TRACKING_HEADER_KEYS`.
2. Add it to `AuthenticatedRequest` + the inbound parse in `serviceAuth` (auth.ts).
3. Thread the resolved value (body `||` header) into the identity objects in `generate.ts`.
4. If it must tag a runs-service cost/run row, that's automatic once forwarded — runs-service reads the header (header > body > parent inheritance). If you persist it locally, add the `email_generations` column + migration.

Every internal client (runs/chat/campaign/brand/key) builds its headers via `buildTrackingHeaders(identity)` — they pick up new dimensions for free.

**EGRESS GUARDRAIL:** `buildTrackingHeaders` output is for INTERNAL services only. NEVER forward tracking headers to a third-party vendor. This service makes no direct vendor calls (LLM via chat-service), so the strip holds by construction — if a direct vendor client is ever added, it MUST build request headers WITHOUT `buildTrackingHeaders`.

`x-audience-id` is the campaign-chosen priority audience; it's optional (absent outside a campaign flow → omit, never throw). Attribution in runs-service is a flat `SUM(cost) GROUP BY COALESCE(runs_costs.audience_id, runs.audience_id)` — no hierarchical rollup, so every cost/run row must carry it. NOTE: the LLM spend is a **chat-service** cost row, not content-gen's; tagging it requires chat-service to read `x-audience-id` inbound (separate repo).

`offerId` is the campaign's offer (brand-service offer entity) and it is a **BODY field, never a header** — it is deliberately NOT in `TRACKING_HEADER_KEYS`. workflow-service threads `results.<start_run>?.offerId` into the request BODY of the `/generate` callee (workflow-service #431); no producer in the fleet emits an offer header, and inventing one would spread a wire format nobody sends AND bypass the single-brand guard below on a multi-brand request. It reaches brand-service because `/generate` puts the resolved value on the `Tracking` identity, which `brand-client` reads.

brand-service refuses brand-scoped reads with **409 SEVERAL_OFFERS** once a brand sells 2+ offers (21 of 144 brands with offers, measured 2026-09-17), so `extractBrandFields` includes `offerId` in the extract-fields request BODY (the key brand-service reads — verified against its `src/schemas.ts`) **only when `brandId` names a single brand**: brand-service 400s an offerId sent with several brands, so multi-brand CSV requests stay brand-scoped and byte-identical to pre-offer behaviour. Never guess or default an offer — absence stays absence (the request stays brand-scoped and multi-offer brands keep the pre-existing fail-soft path). Do NOT move the single-brand guard into the routes: `brand-client.ts` is the one place that knows how `brandId` is spelled on the wire.

**This path is only HALF the fix and is inert until workflow-service re-lands it.** The failing step in the live incident (campaign `647572d9`) is `brand_extract_fields` — a DAG step calling brand-service DIRECTLY, not through this service. workflow-service #431 covered both callee shapes and was reverted by #432 ("breaks every campaign run"), so nothing sends `offerId` here yet. The pitch route deliberately does NOT accept it: it makes no extract-fields call, so the field would be API surface with no behaviour.

The email templates declared at most eleven inputs about the recipient (name, title, headline, and seven company fields), while lead-service serves a great deal more: seniority, departments, functions, city, state, country, timezone, business languages, LinkedIn profile, the full employment history, and on the organization side the short public description, industries and secondary industries, founded year, annual revenue, total funding and funding events, website, LinkedIn page and headquarters location. - **The extra facts are NOT tokens in the template bodies.** The bodies are stored rows, hand-tuned per org across dozens of versions (`cold-email-v9` … `cold-email-v41`, `blind-discovery-email-v26`, `feedback-request-*-email-v1`), and a `{{token}}` added to one of them reaches only that one: a fork written tomorrow would not have it, and rewriting stored copy destroys tuning that cannot be recovered. Same reasoning, and the same home, as the language directive above.
- **They arrive as optional variables and are rendered in a `Recipient context` block ahead of the template** (`src/lib/lead-context-block.ts`). Catalog of accepted names, with descriptions and the label each renders under: `src/lib/lead-context-variables.ts`. Both are standalone leaves; the block takes its value renderer as an argument so it never imports `chat-service-client.js`, which most unit suites mock.
- **A caller that sends none of them gets a byte-identical prompt.** The block is empty when nothing applies, and nothing about the request or response shape changed, so every existing DAG keeps working untouched and no template type was versioned.
- **A fact the template body already consumes via `{{token}}` is never repeated in the block.** The builder reads the template's tokens and skips those names, so an existing template renders exactly as it always did.
- **Only catalog names are rendered.** An unrecognised variable is left alone, exactly as before; the block is not a dump of everything the caller sent.
- **`leadBuyingSignal` is the one structured entry** (`{ type, occurredOn, fact, source, sourceUrl }`, sent by workflow-service as lead-service serves it on a lead from a signal audience; ABSENT for every other lead). It renders under its own "Recent buying signal" heading through a dedicated `format` (`formatBuyingSignal`): the quotable `fact`, its kind and its date. `source`/`sourceUrl` are provenance and never reach the prompt. A value without a usable `fact` renders nothing (logged) — the signal is never rebuilt from its other fields, and an absent key leaves the prompt byte-identical. **Only `hiring` / `job_change` / `funding` may be quoted** (`QUOTABLE_BUYING_SIGNAL_TYPES`): any other kind, today `linkedin_engagement` (a like/comment on a competitor's post, owner 2026-10-03: reads as surveillance), is dropped by `withoutUnquotableBuyingSignal` at the top of `generateFromTemplate`, before token substitution AND the context block, so the prompt is byte-identical to a lead with no signal. The signal chose the recipient; it never shapes the message. A new kind is unquotable until listed.
- **`leadQualification` carries the offer's checks on the recipient's company** (lead-service `lead.qualification`, `{ domain, checks: [...] }`, verbatim). Rendered by `formatQualificationChecks` under "Checks we ran on their company": per check the question, role (`must_pass` = Hard filter, `mention` = Bonus), outcome (pass / fail / could not check / not checked yet), evidence, reason when not judged, screenshot link. Passed AND failed checks both go in (owner 2026-10-07). Context only: no sentence tells the model to cite it; a template that wants it says so (`{{leadQualification}}` gets the generic render and drops it from the block). `checks: []` renders nothing silently, so the prompt is byte-identical. Never re-judge or summarize a check here.
- **`leadRelationship` says who the recipient ALREADY is to the brand** (RELATIONSHIP-TAGS-1014; workflow-service's shared relationship step: lead-service tags judged on crm-service's merged thread). `src/lib/lead-relationship.ts`, leaf: NOT in `LEAD_CONTEXT_GROUPS` (the generic block never renders it), published in `contextVariables` beside them. Two halves: the facts (`lines`, `threadLines`, `eventLines`) as a "Who this person already is to us" section ahead of the recipient context, and the caller's `strategy` verbatim appended LAST to the system prompt (after the campaign instruction), where it wins over a template written as a first contact and over an instruction assuming one. Absent, or no recognised `state` = both prompts byte-identical. Never restate the strategy text here or branch per tag: the caller owns the game, identical in every writer.
- **The catalog is published on every prompt read** (`GET /prompts`, `GET /platform-prompts`) as `contextVariables`, a sibling of `variables`. It is deliberately NOT merged into `variables`: that field means "tokens this body declares" and the fork guard (`assertPromptVariablesMatch`) requires a submitted prompt to match it exactly, so widening it would 400 every fork and confuse workflow-service's variable-coverage validation. Same list for every type, since every template accepts them.

## The email is written in the recipient's language, not always in English

Every cold email went out in English, including to the ~10% of leads who are not in an anglophone country (measured on 30 days of prod leads: 5424 US / 240 UK / 136 CA against 41 DE, 38 FR, 32 PL, 21 SE, 19 IT, 14 NL, …). Nothing in the chain carried a language: the variables that reach `/generate` are the lead's name, title, headline and company facts — no country, no city, no domain — so the model had no signal and answered in the language of the prompt.

- **The language is produced upstream, never derived here.** human-service is the canonical producer of the person and derives the list (it already threads a per-person `timezone` through this same chain for send-scheduling — language is the same gesture); lead-service carries it on the lead. This service only *selects* from it. Do NOT re-derive a language from geography, from the lead's name, or from the company description — that is read-side derivation of a value the writer already held.
- **The list is ORDERED, most plausible first, and that ordering is the contract.** Selection is by position. An unordered list makes `resolveLeadLanguage` meaningless. Values are ISO 639-1 lowercase codes (`de`, `fr`, `it`); the directive needs a NAME, so `languageNameFromCode` resolves the code through `Intl.DisplayNames` rather than a hand-written table. An unresolvable code emits NO directive and logs — instructing a model to "write in zz" is worse than not instructing it.
- **The selection rule is English-preferring** (`src/lib/lead-language.ts`): absent/empty → English; **contains English anywhere → English**; otherwise the first entry. Deliberate, chosen 2026-08-26: a recipient who can do business in English gets English even when another language leads the list, so the directive only ever fires for someone with no English at all. This bounds the feature to a fraction of the non-anglophone population — that is the intent, not a bug. Do not "fix" it into first-wins without asking.
- **English means NO directive**, so the system prompt is byte-identical to what it was before this existed. An absent list is the producer truthfully saying it does not know; English for that case is a documented consumer decision, not a fabricated value.
- **The directive lives in `GLOBAL_SYSTEM_PROMPT`, not in the prompt templates** (`buildLanguageDirective`). Bodies are hand-tuned per org across dozens of versions (`cold-email-v9` … `v38`, `blind-discovery-email-v26`, …); a rule placed in the system prompt reaches every one without editing a single stored row. The directive says explicitly that the English instructions are the language of the *prompt*, not a model for the output — without that line a model handed English instructions and English example copy answers in English.
- **The lead is read by `leadId`, not threaded through the workflow DAG** (`src/lib/lead-client.ts` → `GET /orgs/leads/{id}`, field `businessLanguages`, shipped in sales-lead-service v0.57.1 / human-service v0.40.0). 908 workflows across 570 dynasties call this service; any one not re-templated would silently keep writing English, so "always" could not hold there. `leadId` is present on 100% of generations. Needs `LEAD_SERVICE_URL` + `LEAD_SERVICE_API_KEY` (shared key, set 2026-08-26).
- **A lead-service failure never fails the generation** — it logs loudly and degrades to English, which is exactly the pre-feature behaviour. It is a read, before anything is written or billed. Same shape as the brand-field extraction directly above it in `/generate`.
- The lookup runs **after** the stored-generation retry path, so a retried lead still costs zero downstream calls.

## One email per lead per campaign — `/generate` answers a retry from storage

`idx_emailgen_lead` is UNIQUE on `(campaign_id, lead_id)`: a person gets ONE first-touch email per campaign, so nobody ever receives two different openers. That invariant is load-bearing — do NOT drop the index — but until v0.28.3 nothing read it before doing the work. A legitimately retried lead (sales-lead-service#443 hands back leads that were paid for, served, and never contacted) re-entered the route, ran the chat-service completion, got billed, and only then hit the index and threw. The throw failed the whole workflow run, so the person still went uncontacted and the completion was discarded: 445 failed runs against 33 completed on one prod campaign in a day, ~$42 of a paying customer's budget, 592 duplicate-key errors across 4 campaigns in 48h (issue #186).

- **`POST /generate` looks the lead up BEFORE any downstream call** — before prompt resolution, campaign context, brand-field extraction and the completion. `leadId` present + a row for `(orgId, campaignId ?? "", leadId)` → return that generation. The lookup normalizes `campaignId` to `""` exactly as the insert does; using the raw nullable value would miss the rows it stores.
- **The answer is the STORED email, never a fresh one.** These leads were never contacted, so nothing about the email is stale to its recipient — and a fresh one is not storable anyway (the index forbids a second row and `email_generations` is the append-only bronze layer). "A different angle after a failed send" belongs to a replied/bounced population that does not exist here. A second generation for one `(campaign, lead)` is not legal; the index says so and the route now agrees with it.
- **Response shape is identical to a fresh generation** (`toGenerationResponse`, shared with the `idempotencyKey` hit) so no caller branches and the run continues to its push step. `tokensInput`/`tokensOutput` are the ORIGINAL completion's counts — cost truth is chat-service's rows, so never sum these as spend.
- **`idempotencyKey` is the wrong key for this caller and always was.** The cold-email workflow sends none (`generate-start … idempotencyKey=none` on every trace), so that branch is dead code on this path; `(campaign_id, lead_id)` is the real uniqueness in play.
- **The insert still catches the race.** Two concurrent retries of one lead both miss the lookup; the loser catches `23505` on `idx_emailgen_lead` specifically and returns the winner's row. Narrow by construction: no `leadId`, a different constraint, or no row readable back all rethrow. That completion is wasted — the lookup is what keeps the race rare rather than routine.
- Trace events distinguish the paths: `lead-generation-hit` (lookup, nothing billed) vs `lead-generation-race` (warn, one completion discarded). Neither creates a runs-service run, same as `idempotency-hit`.
- Known gap, rare and non-fatal: lead-service's `repointed_from_lead_id` repair can move a person's `lead_id` after their generation was written. The lookup then misses, a second email is generated and stored under the new id — one extra paid email, not a failed run.

## Every served step carries a delay (`src/lib/sequence-delays.ts`)

email-gateway `POST /orgs/send` requires a numeric `daysSinceLastStep` on every step and 400s the whole send otherwise. glm and deepseek answers (Aug 25 to Sep 15 2026) dropped it, mostly on step 1, and 13 rows were stored that way. The lead-retry path re-served two of them 41 times each (82 failed sends, 2026-09-21 to 09-25).

- `withSequenceDelays` is the one rule, applied at generation (inside `parseSequenceFromJson`, before the insert, so no bad row is ever stored) and in `toGenerationResponse` (every stored answer: lead retry, idempotency, race).
- Step 1 without a delay is `0`. Nothing precedes the first email, so that is the definition, not a guess.
- A later step without a finite non-negative delay throws `IncompleteSequenceError` → `/generate` answers **502** naming the generation and steps. That wait is the model's choice and cannot be derived, so it is never filled.
- Do not "fix" the gateway's requirement or default follow-up delays here.
- **An unusable answer is regenerated once before it fails** (`MAX_GENERATION_ATTEMPTS = 2` in `generateFromTemplate`): an `IncompleteSequenceError` or chat-service's 502 `"LLM returned invalid JSON."` (glm/deepseek, stochastic) re-asks the same request; the last attempt's error is thrown unchanged. 402, 429, 400, generic 5xx and connect errors are never regenerated here. chat-service bills each `/complete` itself; stored tokens sum every completion that returned. Each regeneration logs `[content-gen] regenerating unusable sequence` + trace event `llm-regenerate`.

## Serving the copy that was written (`bodySource`)

`POST /generate` never writes `body_text` / `body_html`; it writes `sequence`. Every row created since February 2026 therefore has NULL body columns and a populated sequence, and every read that returned the row whole handed consumers a subject with no words. lead-service reads the top-level `bodyText` to assemble a person's history, so the dashboard's "Email we wrote" row rendered empty for every lead contacted since February — silent for seven months because an empty string reads the same as "no copy exists".

- **Resolved on READ, not backfilled.** `withResolvedBody` wraps the row in `GET /generations`, `GET /generations/by-lead/:leadId` and `GET /generations/by-enrichment/:id`; `toExampleEmail` does the same for `GET /generations/examples`. One resolution fixes all ~45,000 historical rows with no migration, and the append-only bronze log stays untouched.
- **Precedence: columns, then sequence, then nothing.** A populated legacy column wins (pre-Feb-2026 rows are byte-identical to before). Otherwise the FIRST step carrying copy — that step is the email the recipient was sent; the later ones are the planned follow-ups. Missing HTML is regenerated with `textToHtml`, the exact generation-time conversion, never a second implementation.
- **`bodySource` is the field that makes absence legible**: `column` | `sequence` | `none`. Copy that genuinely does not exist is `bodyText: null` + `bodySource: "none"`, never `""` — an empty string for both cases is what hid this.
- **The sequence is still returned whole.** lead-service forwards it as the planned cadence; nothing is dropped and no field was removed, so existing consumers keep parsing.
- Do NOT ask a consumer to reach into `sequence` itself — "what did we write to this person" is this service's question to answer.

## Response-size bounds (the OOM class)

A generation row carries the full prompt, the raw model response and the whole sequence — **~52 KB per row in production**, and one brand holds >10,000 of them (~542 MB of row text; several times that once it is JS objects plus one JSON string from `res.json`). Against the container's ~2.09 GB V8 default ceiling, any read that materializes a whole brand's or campaign's history is a `FATAL ERROR: Reached heap limit`, which Docker answers with a restart — so the caller sees a dropped connection, every in-flight generation on the cold-email path dies, and nothing in the logs names the request that did it (issue #183: 6 crashes in 24h, 4 inside 90 seconds).

- **`GET /generations` is bounded at `MAX_GENERATIONS_PER_RESPONSE` (2000) rows** (`src/routes/generate.ts`). With an explicit `limit` (1..2000) + `offset` it pages; without one it reads `MAX+1` and **refuses an oversized set with 413** naming the ceiling. Never trim to the cap and return anyway — a partial list that looks whole is the failure this bound exists to prevent. `api-service` already forwards `limit`/`offset` on `GET /v1/emails`; `GET /v1/campaigns/:id/emails` does not yet and will 413 on a campaign over 2000 generations (api-service#841).
- **Never count by reading rows back.** `count(*)` in SQL, not `findMany(...).length` — `POST /stats` did the latter and grew with the org's whole history for no gain.
- **Never buffer a remote body whole.** `Buffer.from(await response.arrayBuffer())` is unbounded; use `readCappedBody(response, maxBytes)` (`src/lib/capped-body.ts`), which checks the declared `content-length`, streams against a hard ceiling, cancels the download on breach, and throws `PayloadTooLargeError` → 413. `POST /compose` caps its source video at `MAX_SOURCE_VIDEO_BYTES` (150 MiB); the composed output and the blob upload are still buffered whole, so that ceiling is what keeps the three of them inside the heap.
- **Inbound JSON is capped at `JSON_BODY_LIMIT` (100kb)** (`src/lib/json-body.ts`, mounted in `src/index.ts`) — express's own default, made explicit and surfaced as a readable 413 naming the limit that refused it (`respondIfBodyTooLarge`) instead of an opaque 500. **The two writer doors, `POST /generate` and `POST /generate/materials`, take up to `WRITER_JSON_BODY_LIMIT` (1mb)** (EMAIL-413-1030): a script-writer body carries the script's whole traced answer (system prompt with the brand context, chat's answer) + `units` + `variables`, so its size grows with the BRAND, not the lead. Doc Dinners hit ~145-165 KB on EVERY lead (2026-10-29: 100% of its main campaign's runs 413'd, 0 emails for ~20 h; 3 other orgs hit it too, largest body seen 229 KB). Never truncate or slim what the script wrote to fit: the stored row must be the email written. Every other route keeps 100kb. Pinned by `tests/unit/json-body.test.ts`.
- **Do not answer this class by raising `--max-old-space-size`.** That moves the crash; it does not remove it. `NODE_OPTIONS` on the container is `--dns-result-order=ipv4first` and the ceiling is the V8 default — a raise is fine *alongside* a real bound, never instead of one.

## Request logging

`src/middleware/request-log.ts` is mounted **before body parsing and before auth**, so every request is named even when it never reaches a handler (oversized body, bad key, unknown path). A fatal OOM gives no chance to log on the way out, so the line that identifies the culprit is written when the request **starts** — after a heap-limit crash, the last `[req] ->` line before the fatal is the request that took the process down.

```
[req] -> POST /generate inBytes=8214 org=<uuid> run=<uuid>
[req] <- POST /generate 200 ms=4120 inBytes=8214 outBytes=19233 org=<uuid> run=<uuid>
```

Method, path, byte counts and the identity/attribution headers already used for tracking. **Never the body, never query values, never generated content** — the sizes are the diagnostic, the payload is not.

## Gotchas

- **pnpm only** — the tracked lockfile is `pnpm-lock.yaml`. Never commit a stray `package-lock.json`; delete it before committing.
- **Unit tests fully-mock `src/db/schema.js` and `src/middleware/auth.js`** (full `vi.mock` replacement, NOT `importOriginal`) — ~12-18 files each. So a route/module that reads a NEW export from either at **module-eval time** (an express middleware arg in `router.get(path, mw, h)`, or a top-level `const cols = { id: view.id }`) crashes EVERY one of those test files with `[vitest] No "<export>" export is defined on the "<module>" mock`, even though the test never exercises that route. Fix: **defer the access past module-eval** — wrap the middleware in an arrow (`(req,res,next) => newAuthFn(req,res,next)`) so the binding is read at request time, and build column/select maps lazily inside the query function, not at top level. Do NOT add the export to all N mocks (brittle — the next new export re-breaks them). Reference: `src/routes/generate.ts` `/generations/examples` middleware wrap + `src/lib/examples-query.ts` `silverColumns()`. **The SAME class extends to ANY module many suites `vi.mock` without re-exporting its constants — not just schema.js/auth.js.** `src/lib/chat-service-client.js` is `vi.mock`'d by ~13 suites; when `schemas.ts` imported a new `CHAT_MODELS` const from it for a top-level `z.enum(CHAT_MODELS)`, every one of those 13 crashed at module-eval with `z.enum(undefined)` (`CHAT_MODELS` was undefined under the mock) — and `schemas.ts` is reachable from every route, so it cascaded. Fix: **keep module-eval-read constants in a standalone, never-mocked module** (`src/lib/chat-models.ts` holds `DEFAULT_MODEL`; the old `CHAT_MODELS` enum is gone since LLM-DYNASTY-1022-CG). Rule of thumb: before importing a const into `schemas.ts` (or any top-level `z.enum`/`z.literal`/column-map), check whether the source module is `vi.mock`'d anywhere — if yes, move the const to its own leaf module. **Run the FULL `pnpm test:unit` locally before pushing** (not just your new test file) — this whole class breaks sibling suites and only the full run surfaces it; there is no local DB so CI is the ONLY gate for integration, making the local full unit run your one pre-push safety net.
- **Adding a LINK to the `db.insert(...).values(...).returning()` CHAIN breaks all 15 hand-rolled db mocks — same class as the new-export gotcha above, one level down.** The unit suites stub `db.insert` as `vi.fn().mockReturnValue({ values: vi.fn().mockReturnValue({ returning: ... }) })`, so inserting `.onConflictDoNothing()` between `values` and `returning` makes the chain return `undefined` and every suite that reaches `/generate` flips to 500. Fifteen files hand-roll that chain (`git grep -l returning tests/unit`), and teaching each one the new link is brittle — the next chain method re-breaks them all. Prefer a form that leaves the chain alone: for the `(campaign_id, lead_id)` retry race, `/generate` wraps the plain insert in a `try` and matches the postgres.js unique violation (`err.code === "23505" && err.constraint_name === "idx_emailgen_lead"`), which is a bare statement outside any transaction so there is no aborted-tx state to worry about. That is a targeted conflict resolution, not a swallowed error — any other code, any other constraint, and any unreadable-back row all rethrow.
- **`pnpm` itself is broken in the Conductor shell on this machine** — corepack + node 20.19.1 throws `ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING` before any script runs, so every documented `pnpm run *` command in this file dies with a stack that looks like a build failure and is not. Run the pieces directly instead: `npx tsc --noEmit` and `npx tsx scripts/generate-openapi.ts` cover `pnpm run build`, and `rtk proxy npx vitest run tests/unit` covers `pnpm test:unit` (`--project unit` does not exist — the script is a path filter, not a vitest project).
- **A one-shot repair script's DRY-RUN does not exercise the WRITE — the first `--apply` is the first time the update is ever bound.** The dry-run reads, decides, and prints; every parameter-binding, casting and driver quirk on the write path is untested until the run that touches prod. Concretely here: postgres.js `sql.json()` rejects a top-level ARRAY (it hands the value to `Buffer.byteLength` → `ERR_INVALID_ARG_TYPE: Received an instance of Array`), and a stored `sequence` is always an array — so `scripts/repair-escaped-line-breaks.ts` passed its dry-run cleanly and crashed on the first UPDATE (fixed in v0.28.1: bind `JSON.stringify(value)` and cast `::jsonb`). It failed before any write, but a script that had already written N rows would have stopped mid-sweep. So: for any repair/backfill, either exercise the write against a throwaway row first, or accept that the apply run needs the same attention as the dry-run — and always SNAPSHOT the rows the dry-run says it will touch (`.context/pre-repair-snapshot-*.json`) before the first `--apply`, so the write is reversible.
- **Integration tests run only in CI, against a `postgres:16` service container created for that run and destroyed with it — the database starts EMPTY.** (It used to be a Neon branch forked from production; Neon is gone.) Three consequences: (1) **`tests/setup.ts` replays the whole `drizzle/` journal from nothing, fail-loud.** A migration statement that only works against an already-populated database now aborts the replay — that is how `0000`'s bare `ALTER TABLE "email_generations" DROP COLUMN`, sitting BEFORE its own `CREATE TABLE`, was finally caught. `tests/unit/migration-empty-db-replay.test.ts` pins the class without a database: every statement naming a relation must guard itself (`ALTER TABLE IF EXISTS`) or name one an earlier migration creates. (2) **A new migration must be replayable from empty**, not just applicable to prod — write `IF EXISTS` / `IF NOT EXISTS` guards, and put a data backfill after the DDL it depends on. (3) **A failing integration test on the staging→main merge commit makes the deploy SKIP** (it gates on the merge commit's check-suite) — the deploy shows `in_progress`→`inactive`, never `success`.
- **Two `drizzle/*.sql` files are NOT in `meta/_journal.json` and have never been run by the migrator**: `0001_fix_emailgen_indexes.sql` (superseded — `0000` already creates those indexes non-unique, confirmed against prod) and `0012_rename_delaydays_to_daysssincelaststep.sql` (a one-shot data backfill applied by hand). A file in `drizzle/` is inert unless the journal lists it; the journal is the source of truth, not the directory.
- **`pnpm db:generate` prompts on pre-existing drift** — the deprecated `content_generations` table is out of sync with the meta snapshots, so drizzle-kit asks create-vs-rename for unrelated columns. For a simple new table, hand-author `drizzle/<n>_*.sql` (`CREATE TABLE IF NOT EXISTS`) + a matching `drizzle/meta/_journal.json` entry (`when` > the previous entry's). The runtime migrator only checks the journal `when`, not snapshots.

## Signed-out preview email (`POST /preview-email`)

ONE cold email for a brand of the calling org + a sample recipient (name, title, company, optional domain/headline/industry/description, optional `audience` and `offerId`), for the signed-out onboarding's last screen. Source: `src/routes/preview-email.ts` + leaf `src/lib/preview-email.ts`.

Dropped, never repaired. ## The offer's give lists (`giveForFree` / `neverGive`)

In onboarding the customer states, per offer, what they give for free to a prospect who replies (a free audit, a trial) and what they will never give (discounts, free implementation). brand-service stores both as confirmed offer user-fields (#584). Every email uses a free-give item as the ask and never offers a won't-give item.

- **Read here, not threaded through the DAGs.** `/generate` reads `GET /orgs/brands/{brandId}/offers/{offerId}/user-fields` itself when the run names an offer and exactly one brand. workflow-service injects `offerId` into every `/generate` body at compile time (its CLAUDE.md, #433), and all live campaigns carry one (19/19 ongoing, 2026-09-29), so every cold-email workflow gets it with no DAG edited. `/preview-email` reads the same view (by `offerId`, or the brand's sole offer).
- **Confirmed values only, never extract-fields.** extract-fields answers an unconfirmed key by extracting it from the site, which would invent a promise. The user-fields view does no extraction and its `suggested` half is ignored.
- **Empty = nothing.** Both lists empty → no rule, system prompt byte-identical. No fallback text is ever written.
- **The rule lives in the system prompt** (`buildGiveListsDirective`), like the language directive, so it reaches every hand-tuned template without editing a stored body. It says it overrides the template's generic call to action.
- **Failure:** `/generate` degrades loudly to no lists (trace `offer-give-lists-unavailable`), same as brand fields and language. `/preview-email` fails loud (`OfferGiveListsError`, brand-service's 400/404/409 passed through, else 502), like its brand intel.
- The preview's highlights can name `offer.giveForFree` (kind `brand`) as a sentence's source; `neverGive` is never a source.

## Fleet-wide sequence feed (`GET /internal/sequences`, LIVE-RESEARCH-1018)

features-service serves the staff Research studies live and attributes each prospect's outcome to what wrote their emails. Only this service knows that: a DAG names a model ALIAS and most name no template. The feed gives, per stored generation (campaign x lead, every org, since inception): concrete `model`, `promptType` (version included), `workflowSlug`, `createdAt`, `runId` (the workflow run) + `generationRunId` (ours), and `firstEmail` = three deterministic classes of the first email's text.

- **API key only**, no identity headers; `featureSlug` required (cold email = `sales-cold-email-outreach`). Rows without `lead_id` are not served.
- **Incremental**: keyset on `(created_at, id)` with an opaque cursor, index `idx_emailgen_feature_created` (`drizzle/0033`). A consumer stores `nextCursor` and reads only what is new; never a full re-read. Rows younger than 60 s are held back (a row is stamped at insert START, so a later-stamped row can commit first; serving it would skip the earlier one forever).
- **Selects only what it needs**, never `prompt_raw`/`response_raw`/`variables_raw`. Body resolved with `resolveGenerationBody` (same precedence as every other read).
- **What writing it cost (MODEL-RUN-COST-1024-CG)**: each entry serves `completionRunIds` (the chat-service `complete` run(s) whose cost rows ARE the LLM cost of writing it; two when regenerated), `completionRunsReason` (why null; null when set) and the recorded `tokensInput`/`tokensOutput`. chat-service's answer names no run, so `src/lib/completion-runs.ts` (pure) finds it by the `actual` `*-tokens-output` quantity = stored `tokens_output`: children of our run since P1 (2026-10-24), our own run Feb-Mar 2026, else the ONE matching `complete` sibling under the caller's run (prod 2026-10-24: 2,802/2,806). ## Script writer: the fleet's cold emails are written by a stored script (FACTORY-P3, owner 2026-10-29 « 3.B »)

Every workflow that wrote through `/generate` now writes with workflow-service's stored script `message_written/dy_template_writer_full` (the port of `generateFromTemplate` that also builds the system prompt, proven 100 % on recorded generations). Everything this service did around the completion stays here (`src/lib/script-writer.ts`); the DAG runs three steps where it ran one:
- **`POST /generate/materials`** (same body as `/generate`): every step before the completion (idempotency + one-email-per-lead hits, stored template, campaign context, unfilled brand fields, language, give lists, instruction, the asked model + its catalogue provider) → `{ existing, subject, units, tactics }`. `existing` set = the request is already answered: the script step is skipped. Writes nothing; `leadId` required (400).
- workflow-service **`POST /orgs/scripts/run`** with `recordedBy: "content-generation"` + `trace: true`: the script's own run (child of the workflow run) carries the completion and its cost and DECLARES NOTHING.
- **`POST /generate` with `written` (+ `units`)**: no completion, no `single-generation` run; stores the same row (prompt_raw = the sent message, response_raw = chat's whole answer, chat_request + chat_request_inputs read off the traced call and the units, generation_run_id = the SCRIPT's run) and its ONE `message_written` declaration through `declareStoredOutcomes` on that run. Pinned by `tests/unit/generate-script-writer.test.ts` (materials = what `/generate` builds from; the recorded row = the service path's row but the run id).

## Brand transfer (`POST /internal/transfer-brand`)

Fleet contract driven by brand-service: move every row of one brand from `sourceOrgId` to `targetOrgId`, rewrite the brand id to `targetBrandId` when given, idempotent. Only `email_generations` is brand-tied here; the audit of every table lives in the `src/lib/transfer-brand.ts` docstring and must be redone whenever a table gains an org, brand or campaign column.

## A lead's email, per campaign

`idx_emailgen_lead` is unique on `(campaign_id, lead_id)`, so a person holds exactly one generation per campaign — and a person contacted by several campaigns of ONE brand holds several. Measured in production 2026-09-03: **3,193 leads carry two or more**, up to six. The brand scope on `GET /generations/by-lead/:leadId` does not separate them, so that read answered with whichever row the planner picked.

- **`?campaignId=<id>` scopes the read to one campaign**, alongside the existing `?brandId=`. Both narrow, both optional, and they combine. Absent both, the read is byte-identical to what it was before either existed (same single WHERE, no ordering) — the unscoped and brand-scoped callers see no change.
- **No campaign is ever inferred.** Without the parameter the route does not guess, does not pick the newest campaign, and does not hand the caller a list to choose from. A campaign that never wrote to the person is a 404, which is the honest answer, not an error.
- **The campaign is already on the row.** `campaignId` is a NOT NULL column and the route returns the generation whole, so any caller — scoped or not — can read which campaign the email it got belongs to. Nothing new had to be added to the payload for that.
- `POST /generate` normalizes a missing campaign to `""` on insert, so the filter is a plain equality with no null handling.
- The query lives in `src/lib/lead-generation-query.ts` (`findGenerationForLead`) rather than inline in the route, so the integration suite can exercise it against a real database — the unit suites mock `db` entirely, and a mocked `findFirst` cannot show that per-campaign reads return different rows.

**Gateway:** api-service `GET /v1/emails/by-lead/:leadId` builds its downstream query string from an explicit whitelist (`if (brandId) params.set(...)`) rather than forwarding `req.query`, so it does **not** currently forward `campaignId` — the dashboard's parameter would be dropped at the edge. That is api-service's repo and its own passthrough convention (its CLAUDE.md #8) to apply; nothing here can fix it.
